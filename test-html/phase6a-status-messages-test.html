Phase 6A Test: Status Messages (WCAG 4.1.3)

📢 Status Messages Requirements

WCAG 4.1.3 Success Criteria: Status messages are programmatically determinable through role or properties so they can be presented to the user by assistive technologies without receiving focus.

Critical for: Screen reader users who need to be informed of status changes

Key ARIA attributes:

  • aria-live="polite" - Announces when user is idle
  • aria-live="assertive" - Announces immediately (use sparingly)
  • aria-atomic="true" - Reads entire region when changed
  • aria-relevant="additions removals text" - What changes to announce
  • role="status" - Equivalent to aria-live="polite"
  • role="alert" - Equivalent to aria-live="assertive"

Status message types: Form validation, loading states, operation results, progress updates, cart changes

🧪 Scanner Testing Guidelines

Expected Scanner Behavior:

  • Status Messages Scanner (4.1.3) should detect:
    • ❌ Dynamic content updates without aria-live regions
    • ❌ Form validation feedback without status announcements
    • ❌ Loading states without accessibility feedback
    • ❌ Progress updates without screen reader notifications
    • ❌ Shopping cart/count changes without announcements
    • ❌ Error messages without role="alert" or aria-live
    • ❌ Search results without status communication
    • ❌ Timer/countdown updates without accessibility
    • ✅ Proper aria-live regions for status communication
    • ✅ Appropriate use of role="status" and role="alert"
    • ✅ Status messages that don't receive focus

Detection Patterns:

  • Form validation: Error/success messages near form fields
  • Loading states: Spinners, progress bars, "Loading..." text
  • Dynamic counts: Cart items, search results, notifications
  • Operation feedback: "Saved", "Deleted", "Added" messages
  • Progress updates: Upload/download progress, multi-step flows
  • Timer displays: Countdowns, session timeouts
  • Error recovery: Network error messages, retry notifications

Required ARIA Attributes:

  • aria-live="polite" - For non-urgent status updates
  • aria-live="assertive" - For urgent alerts (use sparingly)
  • role="status" - Equivalent to aria-live="polite"
  • role="alert" - Equivalent to aria-live="assertive"
  • aria-atomic="true" - Read entire region when changed
  • aria-relevant - Specify what changes to announce

Testing Procedure:

  1. Identify elements that show status/feedback messages
  2. Check for aria-live, role="status", or role="alert" attributes
  3. Verify messages don't receive focus inappropriately
  4. Test with screen reader to confirm announcements
  5. Check timing - messages should be announced when shown
  6. Verify appropriate urgency level (polite vs assertive)

Common Violations:

  • Form validation messages without aria-live
  • Loading spinners without status announcements
  • Cart/count updates without accessibility feedback
  • Error messages that only appear visually
  • Progress bars without verbal progress updates
  • Toast/notification without proper ARIA roles
  • Dynamic content updates without live regions

Success Criteria:

PASS: All status messages have appropriate ARIA live regions or roles

FAIL: Status information only available visually without programmatic announcements
